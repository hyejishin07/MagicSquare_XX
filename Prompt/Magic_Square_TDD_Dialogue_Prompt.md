## TURN 2 — 산출된 프롬프트로 실제 실행

### 🧑 USER

(TURN 1 에서 받은 프롬프트 코드블록을 **그대로** 채팅에 다시 입력)

```
# [Cursor.AI 실행 프롬프트] 4×4 Magic Square — TDD 설계 문서 작성

## 역할 (Role)
너는 **Test-Driven Development 설계 전문가**이자 **Spec-First 사고를 외부화하는 기술 작가**다.
구현 코드는 작성하지 않는다. **테스트가 곧 명세이고, 명세가 곧 설계**라는 원칙으로 문서를 만든다.

## 입력 컨텍스트 (반드시 먼저 읽을 것)
- 참조 문서: `@Report/Magic_Square_Problem_Definition_Report.md`
- 위 문서의 **STEP 1~5에서 확정된 정의·불변식·계약·훈련 목표를 변경하지 말 것.**
- 특히 다음을 그대로 승계한다:
  - 진짜 문제 정의 (STEP 5-2)
  - 7층 불변식 I~VII (STEP 5-3)
  - 훈련하려는 8가지 사고 능력 (STEP 5-4)
  - "검증·생성·풀이·열거" 활동 분해 (Why #2 / Why #3)

## 산출물 (Deliverable)
경로: `Report/Magic_Square_TDD_Design_Report.md`
형식: Markdown, 한국어, 표·코드블록·수식(LaTeX) 적극 활용.
범위: **TDD 설계 문서만**. 알고리즘 의사코드/구현 코드 금지.

## 문서 구조 (반드시 이 순서·이 섹션으로 작성)

### 0. 문서 메타
- 프로젝트, 문서 유형(TDD 설계), 작성일, 선행 문서 링크, 범위 명시
- 범위에서 **제외되는 것 명시**: 구현 코드, 알고리즘 선택, 성능 최적화, UI

### 1. TDD 설계 원칙 선언
- "Red → Green → Refactor" 사이클 정의
- 본 프로젝트에서 채택하는 **Spec-First** 정의
- 테스트의 4가지 역할: 명세 / 회귀 방지 / 설계 압력 / 문서

### 2. 모듈 경계 (Module Boundaries)
선행 문서의 활동 분해를 모듈로 승격한다.
| 모듈 | 책임 | 입력 계약 | 출력 계약 | 의존 |
|---|---|---|---|---|
| Validator (검증기) | … | … | … | — |
| Solver (풀이기) | … | … | … | Validator |
| Generator (생성기) | … | … | … | Validator |
| Enumerator (열거기) | … | … | … | Validator, Symmetry |
| Symmetry (대칭/동치) | … | … | … | — |
| Grid (자료 표현) | … | … | … | — |

- 각 모듈별로 **순수 함수 여부**, **부수효과 위치**, **비결정성 격리 지점**을 명시할 것.

### 3. 자료 모델 & 도메인 계약
- `Grid` 표현(4×4, 셀 도메인, 빈 칸 표현 방식)
- `Cell` 타입, `EmptyCell` 표현 (예: `Option<Int>` 또는 `0` 사용 시 명시)
- 입력 검증 규칙(형태 위반 시 동작 = 예외 vs 결과형)
- 불변식 I~VII를 **타입/계약 레벨에서 어디서 강제**할지 매핑

### 4. 테스트 분류 체계 (Test Taxonomy)
| 계층 | 목적 | 예시 대상 |
|---|---|---|
| L1 Unit | 순수 함수 단위 술어 | `is_magic`, `row_sum`, `is_all_different` |
| L2 Contract | 모듈 계약 검증 | Validator 입출력 계약 |
| L3 Invariant / Property-Based | 불변식 무작위 검증 | I~VII 각 항목 |
| L4 Equivalence (대칭) | 회전·반사 동치 | orbit 닫힘 |
| L5 Integration | 모듈 간 협력 | Solver→Validator 일치성 |

각 계층에 **반드시 한 줄 정의**와 **적용 모듈**을 표로 제시.

### 5. 불변식 → 테스트 매핑 (핵심 섹션)
선행 문서의 7층 불변식 I~VII를 **각각 최소 1개 이상 테스트 시나리오**로 매핑한다.

각 항목은 다음 형식으로 작성:
- **불변식 코드**: (I) 도메인 / (II) 마법합 / … / (VII) 판정 결정성
- **자연어 진술**: 한 문장
- **테스트 의도 (Given/When/Then)**: 의사 시나리오 (코드 아님, 문장)
- **테스트 종류**: L1~L5 중 어디
- **실패 시 의미**: 어떤 가정이 깨졌음을 뜻하는지

> 의사코드/언어 종속 코드를 쓰지 말 것. **Given–When–Then 자연어**만 허용.

### 6. 활동별 TDD 시나리오 (Validator / Solver / Generator / Enumerator)
각 모듈에 대해:
1. **공개 계약 (Contract)**: 함수 시그니처 수준의 입출력 약속 (언어 중립, 의사 시그니처 허용 — 예: `validate(grid) -> {Satisfied | PartiallyConsistent | Violated}`)
2. **Red 단계 테스트 목록**: 최소 5개의 실패해야 할 테스트 (이름 + 한 줄 의도)
3. **Green 단계의 통과 조건**: 어떤 술어가 참이 되어야 통과인가 (불변식 참조)
4. **Refactor 단계의 관심사**: 중복·결합·이름·경계 — 무엇을 정리할지 사전 선언

### 7. 상태 분류 사고 매핑
선행 문서의 3분류 `Satisfied / PartiallyConsistent / Violated` 를
- 유한한 경계 사례(Boundary Cases)
- 동치류(Equivalence Classes)
- 결정 트리(Decision Table)
로 표현하라.

### 8. 대칭·동치(orbit) 처리 설계
- 8개 대칭군(회전 4 × 반사 2)을 다루는 모듈/테스트 책임 위치
- "본질적으로 다른 해 880" 을 **계수 가능성(countable)** 관점에서 어떻게 테스트할지 (대표원 선택 규칙 등)

### 9. 비결정성·시간·무작위성 격리 전략
- Generator에서의 무작위성을 외부 자원(시드)으로 주입하는 계약
- Solver의 탐색 순서가 결과에 영향 주지 않음을 보장하는 결정성 테스트

### 10. Test Doubles & 경계
- 어떤 곳에 stub/mock이 **필요 없는지** 먼저 진술 (순수 함수 우대)
- 외부 자원(파일·랜덤·시간) 경계에만 doubles 허용 — 그 경계 명시

### 11. 테스트 명명 규약 (Naming Convention)
- 형식 예: `subject_state_expected` 또는 `Given_When_Then`
- 한국어/영어 혼용 정책 1가지 선택하고 그 이유 명시

### 12. CI / 실행 정책 (도구 비종속)
- 단위/속성 테스트 분리 실행
- 속성 테스트 최소 시도 횟수 권장값과 그 근거
- 결정성 회귀 테스트의 빈도

### 13. 추적성 매트릭스 (Traceability Matrix) — 필수
다음 형식으로 **하나의 큰 표**를 만들어라.

| 불변식 | 모듈 | 테스트 계층 | 테스트 시나리오 ID | STEP5 정의 항목 | 훈련 능력(#) |
|---|---|---|---|---|---|

- 모든 불변식 I~VII가 **최소 1행 이상** 등장해야 한다.
- 모든 모듈이 **최소 1행 이상** 등장해야 한다.
- 훈련 능력 1~8이 **최소 1번씩** 등장해야 한다.

### 14. 다음 단계 (구현 진입 전 마지막 점검)
- 구현 시작 전 충족되어야 할 게이트 체크리스트
- 본 설계로 막을 수 없는 위험과 그 대응

### 15. 부록
- 용어 정리(선행 문서 용어 + TDD 용어 보강: Red/Green/Refactor, Property-Based Test, Equivalence Class, Boundary Value, Test Double, Contract 등)

## 작성 규칙 (Hard Constraints)
1. **구현 코드 금지.** 의사코드도 최소화. 함수 시그니처 수준만 허용.
2. **알고리즘 선택 금지.** 백트래킹/제약전파/SAT 등 특정 알고리즘 거론 금지(개념적 참고는 부록에서만 허용).
3. **선행 문서의 정의·불변식·훈련 능력을 변경하지 말 것.** 확장만 허용.
4. 모든 테스트 진술은 **Given / When / Then** 형식의 자연어로.
5. 모든 표는 비어 있는 셀이 없도록 채울 것. 모르면 "미정 — 사유" 로 명시.
6. 한국어로 작성. 수식은 LaTeX(`\(...\)`, `\[...\]`).
7. 분량 가이드: 본문 합계 **A4 8~14장 분량**. 표 위주, 산문 최소.
8. 문서 끝 한 줄: `*본 문서는 구현 코드·알고리즘 선택을 포함하지 않습니다.*`

## 진행 절차 (반드시 이 순서로)

2. 위 "문서 구조" 0~15 섹션의 **목차만** 먼저 출력해 사용자에게 확인 요청.

```

- 짧지만 **명확한 OK 신호**다. 모델은 이 한 문장을 받으면 다음을 모두 수행해야 한다.
  1. `Report/` 폴더 존재 확인
  2. `Report/Magic_Square_TDD_Design_Report.md` 작성 (16 섹션, 한 번에)
  3. 작성 후 *자체 검증 체크리스트* (불변식·모듈·훈련 능력 누락 0건) 부착
  4. 사용자에게 다음 액션 후보 제시
- *대화 일관성 신호:* 이 TURN 에서 모델이 다시 목차를 묻거나, 분량 협의로 되돌아가면 *컨텍스트 손실* 이다. 새 세션에서 본 트랜스크립트를 사용할 때는 TURN 2의 ASSISTANT 응답을 **사용자 자신이 직접 재현해 보낸 뒤** TURN 3 을 입력하면 안전하다.

### 🤖 ASSISTANT (기대 산출의 형식)

| 충족 항목 | 검증 방법 |
|---|---|
| **파일 생성** | `Report/Magic_Square_TDD_Design_Report.md` 존재 |
| **섹션 누락 0** | 0~15장 모두 존재, 각 장 1개 이상 표 |
| **불변식 I~VII 매핑** | 5장과 13장에 모두 등장 |
| **모듈 6종 매핑** | 2장과 13장에 모두 등장 |
| **훈련 능력 1~8 매핑** | 13장 자체 검증에서 1~8 모두 ✅ |
| **Hard Constraints 준수** | 구현 코드 0, 알고리즘 선택 0, 모든 표 빈 셀 0 |
| **종결 문구** | `*본 문서는 구현 코드·알고리즘 선택을 포함하지 않습니다.*` 마지막 줄 |
| **사후 안내** | "다음 액션 후보" 3종 이상 제시 |


### 🔧 SYSTEM 메모

- 본 TURN 의 목적은 **메타-메타 작업** 이다.
  - TURN 1 = "산출물을 만드는 도구를 만들어라" (메타)
  - TURN 4 = "그 메타 작업의 과정 자체를 재현 가능한 자산으로 만들어라" (메타-메타)
- 단순한 대화 로그 덤프가 아니라, **다음 세 가지를 동시에 충족하는 구조** 여야 한다.
  1. **재현성** — 같은 결과를 다른 세션에서 만들 수 있어야 한다 → 사용자 입력을 *그대로* 보존
  2. **검증성** — 각 TURN 의 기대 출력을 *형식 기준* 으로 명시 → "올바른 응답인가" 판정 가능
  3. **교육성** — *왜 이 순서인가* 를 SYSTEM 메모로 부연

### 🤖 ASSISTANT (기대 산출 = 본 문서)

| 충족 항목 | 본 문서에서의 위치 |
|---|---|
| 4개 TURN 분리 | TURN 1~4 헤더 |
| 사용자 입력 원문 보존 | 각 TURN 의 🧑 USER 코드블록 |
| 기대 출력 형식 명시 | 각 TURN 의 🤖 ASSISTANT 표 |
| 진행자 의사결정 노트 | 각 TURN 의 🔧 SYSTEM 메모 |
| 재사용 가능한 형식 | 단일 마크다운 파일, 외부 의존 없음 |
