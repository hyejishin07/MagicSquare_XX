## 사용 방법

이 문서는 **재현 가능한 대화형 프롬프트 세션**입니다. 새 세션에서 아래 순서대로 프롬프트를 입력하면, 동일한 문제 정의 워크플로를 다시 진행할 수 있습니다.

| 기호 | 의미 |
|------|------|
| **USER** | 사용자가 입력하는 프롬프트 |
| **ASSISTANT** | 기대되는 응답 방향 (가이드) |
| **규칙** | 해당 단계에서 반드시 지켜야 할 제약 |

## Turn 0 — 세션 시작

### USER

```text
당신은 문제 정의 전문가입니다.
나는 4x4 Magic Square 프로그램을 만들려고 합니다.
하지만 바로 설계하거나 구현하지 마십시오.
먼저 문제 인식 단계부터 진행하십시오.
```

### ASSISTANT (기대 응답 방향)

- 설계·구현 없이 **문제 인식**만 수행
- 5가지 관점 제시: 배경/동기, 현상, 이해관계자, 기대 가치, 제약
- "마방진을 만든다" 대신 **상황·관찰** 언어 사용
- 사용자에게 맥락 좁히기 질문 (선택)

## Turn 1 — STEP 1: Observation (관찰)

### USER

```text
--------------------------------------------
STEP 1 — Observation (관찰)
--------------------------------------------
다음 질문에 답하십시오:
1. 현재 우리가 해결하려는 상황은 무엇인가?
2. 왜 4x4 마방진 문제를 다루는가?
3. 이 문제는 어떤 학습 또는 시스템 설계 맥락에서 등장하는가?
"마방진을 만든다"는 표현 대신, 상황을 관찰 관점으로 서술하십시오.
```

### ASSISTANT (기대 응답 방향)

**1. 현재 상황**
- 16칸 + 10개 합 제약의 동시 작용
- 유효 상태 희소성, 검증 vs 구성 비대칭
- 회전·반사 동치의 비가시성

**2. 왜 4×4인가 (문제 자체의 성질)**
- 3×3(해 1개) vs 5×5+(폭발) vs 4×4(880개, 중간 규모)
- 검증 쉬움 / 생성·열거 어려움
- 대칭군(위수 8), 시각적 닫힘

**3. 등장 맥락**
- (a) 알고리즘 (b) CSP (c) 이산수학 (d) SW 설계 (e) 교육 (f) 테스트 설계

**규칙:** 해결책·기능·목표 설정 금지

**다음 연결 제안:**
- STEP 2로 가기 전, 목적 좁히기 (퍼즐 vs 데모 등) — 선택

## Turn 2 — STEP 2: Why #1

### USER

```text
--------------------------------------------
STEP 2 — Why #1
--------------------------------------------
Q: 왜 마방진을 완성해야 하는가?
A를 가정하여 답하고, 그 답에서 드러나는 불편함 또는 구조적 문제를 분석하십시오.
```

### ASSISTANT (기대 응답 방향)

**가정된 답 (A):**
- 임의 배치는 거의 마방진이 아님 → **완성 상태**에 도달해야 문제가 성립
- 완성 없이는 시작·종결 모두 불명확

**드러나는 구조적 문제 (6가지):**
1. 유효 상태의 극단적 희소성 (\(16!\) vs 7,040)
2. all-or-nothing 보상 (부분 진척 무의미)
3. 제약 상호 의존 (한 칸 → 전역 영향)
4. 종결 조건 체감 vs 실제 완성의 거리
5. 탐색 공간 비가시성
6. 1비트 출력 vs 무거운 입력 처리

**핵심 한 줄:**
> 완성은 드물고, 부분은 보상되지 않으며, 한 칸의 변경은 전역에 영향을 준다.

**다음 분기 제안:**
- 분기 A: 사용자가 직접 채우는 퍼즐 → 사람 쪽 한계
- 분기 B: 자동 데모·생성기 → 시스템 쪽 책임

## Turn 3 — STEP 3: Why #2

### USER

```text
--------------------------------------------
STEP 3 — Why #2
--------------------------------------------
Q: 왜 단순 계산이 아니라 프로그램으로 구현하는가?
다음 관점에서 답하십시오:
- 반복 가능성
- 검증 자동화
- 오류 방지
- 규칙 기반 사고 훈련
```

### ASSISTANT (기대 응답 방향)

**가정된 답 (A):**
- 단순 계산 = 1회 정답 / 프로그램 = 반복·신뢰·일반화된 절차

**네 관점:**

| 관점 | 단순 계산 | 프로그램 | 본질 |
|------|----------|---------|------|
| 반복 가능성 | 매번 재구성 | 한 번 정의, 무한 호출 | 사고 비용 구조 |
| 검증 자동화 | 검산의 검산 | 외부 참조 진리 | 신뢰의 구조 |
| 오류 방지 | 오류 숨김 | 오류 드러냄 | 실패의 가시성 |
| 규칙 기반 사고 | 암묵적 규칙 | 명시적 술어 | 문제 정의 훈련 |

**통합 한 줄:**
> 프로그램은 규칙을 외부화하여 신뢰·반복·일반화를 가능하게 한다.

**다음 질문 다리:**
- Why #3: 왜 TDD 방식인가?

## Turn 4 — STEP 4: Why #3 (핵심 발견)

### USER

```text
--------------------------------------------
STEP 4 — Why #3 (핵심 발견)
--------------------------------------------
Q: 왜 이 문제를 TDD 방식으로 설계하려 하는가?
- 무엇이 통제되어야 하는가?
- 어떤 불변 조건이 존재하는가?
- 왜 입력/출력이 명확해야 하는가?
```

### ASSISTANT (기대 응답 방향)

**가정된 답 (A):**
- 명세(spec) < 구현(impl) — 검증 가볍고 구성 무거움
- 판정 기준을 먼저 → TDD 적합

**1) 통제 대상**
- 입력 도메인·격자 형태(완전/부분/빈)
- 상태 의미 (충족 / 부분 일관 / 위반)
- 판정 결정성, 변경 추적, 비결정성 격리

**2) 불변식 (6~7층)**
- 도메인, 마법합 M=34, 합 균등, 전체합 136
- 부분 일관성, 대칭 닫힘, 동치(880), 판정 결정성

**3) 입출력 명확성**
- 입력 닫힘, 출력 이산성
- 불변식 검사 가능, 모듈 계약 = 테스트
- 사용자 신뢰 (블랙박스 방지)

**핵심 발견 한 줄:**
> 이 문제는 '옳음을 먼저 적을 수 있는' 문제이며, TDD에 적합하다.

## Turn 5 — STEP 5: 진짜 문제 정의

### USER

```text
--------------------------------------------
STEP 5 — 진짜 문제 정의
--------------------------------------------
다음을 작성하십시오:
1. 표면 문제 정의 (잘못된 정의)
2. 개선된 문제 정의 (정확한 정의)
3. 이 문제의 핵심 Invariant
4. 우리가 실제로 훈련하려는 사고 능력

− 구현 설계는 하지 마십시오.
− 코드 언급 금지.
− 알고리즘 설명 금지.
− 구조화된 Markdown으로 작성하십시오.
```

### ASSISTANT (기대 응답 방향)

**1. 표면 정의 (잘못됨)**
> "4×4 마방진을 만드는 프로그램을 작성한다."
- 행위 중심, 암묵적 규칙, 계약·불변식·훈련 의도 누락

**2. 개선된 정의**
> 유한 도메인 위 4×4 격자에 대해 '마방진' 술어를 명시적으로 외부화하고,
> 임의 상태에 대해 충족 여부·도달 가능성을 신뢰 가능하게 판단하는 것.

**3. 핵심 Invariant (7층)**
- (I) 도메인 → (II) 마법합 → (III) 합 균등 → (IV) 전체합
- (V) 부분 일관 → (VI) 대칭 닫힘 → (VII) 판정 결정성

**4. 훈련 사고 능력 (8가지)**
1. 규칙 외부화  2. 불변식 중심  3. 계약 기반  4. 상태 분류
5. 검증/구성 분리  6. 대칭·동치  7. 모듈 분해  8. Spec-First
